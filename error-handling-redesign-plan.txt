1. GOAL
======================================================================

Failure handling moves out of user scripts and into the library:

  1. No user-written try/except around submit_requests(). The context
     manager in wrapper.py owns error handling.
  2. No user-written isinstance() checks. submit_requests() returns a
     results object with .ok and .failed.
  3. One call per batch is preserved: queue operations (e.g. read(id)),
     then a single submit_requests().
  4. At exit the context manager prints a tally and the script exits
     non-zero when anything failed.


======================================================================
2. LOCKED DESIGN DECISIONS
======================================================================

D1  The context manager (CascadeWrapperBase.__exit__) owns failure
    reporting and the exit code.

D2  submit_requests() returns ChainResults, a list SUBCLASS. Indexing,
    iteration and len() are unchanged. It adds:
      .ok      list of results from chains that did not fail
               (typed from result_type, so submit_requests(Asset).ok
               is list[Asset])
      .failed  list of ChainFailure records (see D5)

D3  .ok and .failed are properties on the object submit_requests()
    already returns. There is no second call to collect them.

D4  Raw result values stay in the list unchanged (CascadeError objects,
    Exception objects). The CascadeError model itself does not change
    (frozen, extra="forbid", success: Literal[False]).

D5  Failures are classified by WHERE the chain stopped and by exception
    type. Never by exception type alone.

      Stopped at an OPERATION step:
        CascadeError                  -> category CASCADE
                                         (API rejected the request;
                                         no new prefix)
        Network exception             -> category NETWORK
                                         prefix [NETWORK]
        Any other exception           -> category LIBRARY
        (Pydantic validation/parse errors, request-building errors, etc.)
                                         prefix [CASCADE-REST-CMS]

      Stopped at a CALLBACK step:
        Any exception                 -> category CALLBACK
                                         (user code; no prefix)

    Network exception means ANY of:
      - aiohttp.ClientError or a subclass
      - any exception whose class is defined in the aiohttp package
        (check type(exc).__module__ starts with "aiohttp")
      - builtin TimeoutError (this includes asyncio.TimeoutError)
      - ConnectionError
    Keep the matcher in ONE function so the list is easy to extend.

D6  Batch-level failure (the run itself breaks): submit_requests() logs
    it, then RAISES CascadeBatchError (chained with "from" to the
    original). It no longer swallows the error and returns []. An empty
    queue still returns an empty ChainResults without error.

D7  CascadeWrapperBase.__init__ gains exit_on_failure: bool = True.

D8  __exit__ behavior (cleanup - log_exit() and driver.close() - always
    runs first, exactly as today, including its own try/except):

      Exception in flight is CascadeBatchError:
        exit_on_failure True  -> raise SystemExit(1). No traceback; the
                                 message was already logged.
        exit_on_failure False -> propagate unchanged.
      Any other exception in flight (bug in user code, etc.):
        propagate unchanged. Normal traceback, natural exit code 1.
      KeyboardInterrupt / SystemExit in flight:
        propagate untouched.
      No exception, callback failures recorded, exit_on_failure True:
        tally already printed; raise the FIRST callback exception (in
        chain creation order) as a plain exception, unwrapped.
      No exception, CASCADE/NETWORK/LIBRARY failures recorded,
      exit_on_failure True:
        tally already printed; raise SystemExit(1).
      No failures:
        return normally (exit code 0).
      exit_on_failure False:
        cleanup and tally only. Never raise. Results stay available to
        the caller as values.

    If both callback and library-scope failures exist, the callback
    exception is raised (its traceback also yields exit code 1).

D9  Tally line, printed at exit by the logger, ALWAYS:
        "{failed} failed, {succeeded} succeeded"
    Append ": reference log for details" ONLY when at least one failure
    is category CASCADE, NETWORK or LIBRARY. Counts are cumulative
    across every batch in the session. This line REPLACES the current
    "[ERRORS]: N failures - check <logfile>" line in log_exit().

D10 Code after the `with` block does not run when the script exits
    because of a failure (consequence of SystemExit / raise in
    __exit__). This must be documented (docstring + wiki).

D11 The MCP server passes exit_on_failure=False. SystemExit is not an
    Exception subclass and must never escape an MCP tool call.

D12 Callback exceptions and user-code exceptions are NOT the library's
    scope: they surface as plain exceptions, never wrapped, never given
    a library prefix.

3. ASSUMPTIONS - NEED KEITH'S CONFIRMATION
======================================================================

Implement as written; flag each in the report-back.

A1  Prefix placement. [NETWORK] and [CASCADE-REST-CMS] appear on the
    chain's "!ERROR:" line in the logfile, for example:
        !ERROR: [NETWORK] ClientConnectorError: <message> @file.py:123
    and on the console "[ERROR]" line for batch-level failures. The
    prefixes do NOT appear on the tally line.

A2  The logfile name is not added to the tally line (keeps the wording
    Keith asked for).

A3  A chain stopped at a callback counts in "failed" (the x) but does
    not by itself trigger the ": reference log for details" suffix.

A4  A multi-item node (list create/edit) whose result list contains
    errors does NOT stop the chain (existing behavior, keep it). The
    chain is recorded as failed once, with the category of the first
    error inside the list, and is excluded from .ok.

A5  Version bump: recommend 4.0.0 (two breaking behaviors: batch
    failures now raise, and exit_on_failure defaults to True). Keith
    decides before release.

A6  New public types live in a new module, cascade_cms/failures.py, and
    are NOT added to cascade_cms/__init__.py (the narrowed exports are a
    deliberate earlier decision). Users import from cascade_cms.failures.

A7  A broken batch counts every chain in that batch as failed in the
    tally.

A8  Non-Exception results from asyncio.gather(return_exceptions=True)
    (e.g. CancelledError, a BaseException) are classified as category
    LIBRARY.
