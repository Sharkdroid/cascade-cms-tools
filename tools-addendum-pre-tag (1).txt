         New "Step 6 - Verify write operations in stages"; the current

    "Step 6 - Verify write operations in stages. Applies to any script
     that contains a write operation: create, edit, delete, copy, move,
     publish, checkIn, checkOut, siteCopy, editAccessRights,
     editWorkflowSettings, performWorkflowTransition, markMessage,
     deleteMessage, editPreference. Decide by operation, not HTTP
     method: search is a POST but read-only. Read-only scripts skip
     this step.

     Do not hand over a finished script with writes in one piece. This
     skill never runs writes, so the user's own output is the only
     evidence. Build the script one write operation at a time, in the
     order they run:

     a. Tell the user the plan: the write operations in order, and that
        you will add them one at a time.
     b. Write the script with the FIRST write operation only,
        including everything before it (reads, callbacks that build
        payloads) and nothing after it. Print what the write returns
        (for create, the new asset's identifier). Validate it (Step 5).
     c. Tell the user exactly what to run, on a test asset or test site
        where possible. Ask them to paste the full stdout, including
        the tally line, and the exit code (`echo $?`). Say which assets
        the stage creates, changes or leaves behind, so they can clean
        up if you stop here.
     d. Check the pasted output. Proceed only if the exit code is 0,
        the tally shows 0 failed, and the printed result is what you
        expected. A bare "it worked" is not enough; ask for the
        output. If it fails, diagnose from the tally line and the log
        prefix ([NETWORK], [CASCADE-REST-CMS], or none for an API
        error), fix the script, validate again, and ask for the output
        again.
     e. Only then add the next write operation and repeat from c. Use
        the identifiers earlier stages printed. Never look an asset up
        by name in order to delete or overwrite it.
     f. For destructive operations on existing assets (delete, publish,
        overwrite), the stage before the write is a read-only preview
        that prints exactly which assets will be affected. The user
        confirms that list before the write is added.
     g. When the last write has passed, deliver the full script
        (Step 7) and say which stages the user confirmed."

         Worked example to add under "## Examples" (about 10 lines,
         prose only): read an asset, create a new asset from its data,
         delete the new asset. Stage 1 is the read plus create, and it
         prints the new asset's identifier; the user pastes stdout and
         the agent checks it. Stage 2 adds the delete; the user pastes
         stdout again. Stage 1 leaves a new asset behind, so the agent
         tells the user its identifier and that they can remove it by
         hand.

         Planner addition, NOT yet confirmed by Keith - flag it in the

4. LIVE CHECKS - READ-ONLY, AGAINST APPTEST
======================================================================

Claude Code performs ONLY these live checks. Before running any template
live, grep it for write operations (edit, create, delete, copy, move,
publish, checkIn, checkOut, and similar). A template that performs any
write is NOT run live; it is validated and stub-tested only.

[ ] 4.1  Clean run. One read-only template, default wrapper
         (exit_on_failure True). Expect exit code 0 and a tally of
         "0 failed, N succeeded" with no suffix. Show `echo $?`.
[ ] 4.2  Bad identifier. Same template with one deliberately invalid
         identifier. Expect exit code 1, tally
         "1 failed, N succeeded: reference log for details", a
         "!ERROR:" line in the logfile, and no traceback. Show
         `echo $?`. Confirm code after the `with` block did not run.
[ ] 4.3  Network error, read-only. In a LOCAL shell only, point the URL
         at an unreachable host and run one read-only template. Expect

         host.
[ ] 4.4  Asset access. Confirm a known APPTEST asset reads successfully
         end to end (the existing smoke test already covers this; note
